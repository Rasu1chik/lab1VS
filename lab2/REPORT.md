# Лабораторная работа №2. Декомпозиция Fantasy Football

## Цель

Преобразовать монолит первой лабораторной в систему независимо запускаемых
микросервисов. Реализовать регистрацию и обнаружение, централизованную конфигурацию,
единую точку входа, межсервисные вызовы, защиту от отказов и два способа доступа к БД
в приложениях на Reactor.

## Исходная система

Монолит содержал контроллеры, JPA-сущности, бизнес-сервисы и единую PostgreSQL:
менеджеры, реальные клубы, игроки, фэнтези-команды и составы, трансферы, туры,
выступления и лиги. Методы создания состава, трансфера и закрытия тура выполнялись
в транзакциях. Эти транзакционные границы сохранены в игровом сервисе.

## Выбор границ

Выделены два бизнес-контекста. `manager-service` хранит профиль менеджера и отвечает
за его CRUD; `fantasy-service` отвечает за игру. У каждого процесса собственная БД,
драйвер и слой доступа. В игровой БД сохраняются числовые `manager_id`/`owner_id`,
JPA-связи с таблицей менеджеров удалены. Доступ к чужой БД отсутствует.

Клубы, игроки, составы, трансферы и начисление очков оставлены в одном сервисе,
поскольку их согласованное изменение является игровой транзакцией. Декомпозиция
по одной таблице создала бы распределённые транзакции без пользы для этой работы.

## Инфраструктура

`config-server` работает на порту 8888 в native-профиле и читает репозиторий YAML.
Каждый клиент имеет только имя приложения и обязательный URL импорта; рабочие
параметры загружаются с сервера. Eureka на 8761 также получает конфигурацию от
Config Server. URL Config Server служит bootstrap-адресом и не требует Eureka.

`discovery-server` ведёт реестр экземпляров. `api-gateway` на 8080 выбирает сервис
по пути и маршрутизирует на `lb://manager-service` или `lb://fantasy-service`.
Конкретные адреса экземпляров не зашиты в бизнес-клиенты и Gateway.

## Реактивность

`manager-service` использует WebFlux, `ReactiveCrudRepository` и R2DBC PostgreSQL.
Сохранение и чтение возвращают `Mono`/`Flux`; операции составляются через
`flatMap`, `map`, `zip` и `switchIfEmpty`. JDBC-драйвер и JPA в этом сервисе отсутствуют.

`fantasy-service` использует WebFlux и Spring Data JPA. JPA остаётся блокирующим.
`Mono.fromCallable` откладывает обращение до подписки, а `subscribeOn(boundedElastic)`
переносит полную транзакционную операцию на рабочий поток. Это сохраняет
thread-bound JPA-транзакции и не блокирует Netty event loop. Возврат Mono сам по себе
не превращает JDBC в неблокирующий драйвер.

## Межсервисный сценарий

1. Клиент отправляет создание команды в Gateway.
2. Gateway находит игровой сервис через Eureka.
3. Контроллер подписывается на отложенный вызов транзакционного сервиса на worker.
4. Feign-клиент проверяет менеджера в `manager-service`, используя service discovery.
5. R2DBC-сервис возвращает менеджера либо 404.
6. Игровой сервис проверяет состав и бюджет и атомарно сохраняет команду с составом.
7. При недоступности менеджерского сервиса Circuit Breaker/fallback дают 503;
   команда не создаётся.

Обратный Feign-вызов используется перед удалением менеджера: игровой сервис сообщает,
есть ли связанные команды или лиги. Это последовательная проверка с описанной в
README границей согласованности, а не распределённая транзакция.

## Circuit Breaker

Spring Cloud OpenFeign включает CircuitBreaker-обёртку. Resilience4j учитывает
сетевые и серверные сбои; бизнес-ответы 4xx исключены из статистики отказов.
После достижения порога circuit переходит в OPEN и быстро отклоняет вызовы.
Через 10 секунд допускаются пробные вызовы в HALF_OPEN. Успешные пробы возвращают
circuit в CLOSED. Fallback сохраняет 404 для неизвестного менеджера, при отказе
возвращает 503. Успех не имитируется, обязательная проверка не обходится.

## Демонстрация на защите

1. Выполнить команду запуска из README и показать `docker compose ps`.
2. Открыть Eureka Dashboard: Config Server, Gateway и оба бизнес-сервиса.
3. Открыть `/manager-service/default` на Config Server и показать R2DBC-настройки.
4. Через Gateway создать менеджера и запросить каталог игроков.
5. Показать код `ManagerRepository` и WebFlux-контроллера — Reactor + R2DBC.
6. Показать `TeamController` и `TeamService` — Reactor + JPA и транзакция.
7. Показать `@FeignClient`, `FallbackFactory` и настройки Resilience4j.
8. Запустить `python3 scripts/smoke.py --resilience`: остановка сервиса, 503,
   независимые запросы и восстановление связи.

Команды проверок и их фактический результат записаны отдельно в VERIFICATION.md.
Место для ФИО, группы и требований к титульному листу заполняется перед сдачей.
